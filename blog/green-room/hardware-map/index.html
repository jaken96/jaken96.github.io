The Hardware Map: What Runs a Local LLM?

Writing the Initial Setup blog post opened my eyes to how little I know about LLM hardware configuration. I created this post to document my research into various configurations as we continue to develop the green room into something useful. Full disclosure: Codex heavily assisted the creation of this post.

A local model does not run on “the GPU.” It runs through a chain of storage, memory, processors, buses, drivers, and cooling. The slowest useful link sets the pace.

Research checked August 14, 2026 · Inference first, with a short training contrast

Start with three limits

Local LLM hardware gets easier to understand when I ask three questions in order.

1. Capacity

Can the model weights, key-value cache, compute buffers, and runtime headroom fit in the memory that will hold them?

2. Bandwidth

Can that memory feed the active processor fast enough? A large memory pool can still be slow.

3. Compute

Can the CPU or GPU perform the required math quickly, and does the software have efficient kernels for that hardware?

Capacity is a gate. If the workload does not fit, it will fail or spill into slower memory. Bandwidth and compute decide how fast it runs after it fits. Software decides how much of the hardware I can use.

The bottleneck changes during one request

An inference request has distinct phases. A machine can be quick in one phase and miserable in the next.

Phase What happens Common limit What improves it
Load Weights move from storage into RAM and, for GPU work, into VRAM. Storage speed, free RAM, and host-to-GPU transfer speed. An SSD, enough memory, and fewer cold starts.
Prompt processing The model processes known input tokens in parallel. This is also called prefill. Compute throughput and kernel efficiency often matter most. Stronger accelerator compute, larger useful batches, and efficient kernels.
Token generation The model generates one token, then repeats with the new token included. Memory bandwidth often dominates at small interactive batches. Fast active memory and a backend that keeps transfers low.
Long or concurrent work The runtime retains attention state for more tokens and more sequences. KV-cache capacity, memory bandwidth, and allocation strategy. Shorter contexts, fewer parallel sequences, smaller cache types, or more memory.

NVIDIA describes prefill as a highly parallel matrix-matrix operation. It describes decode as a sequential matrix-vector operation where memory movement often dominates latency [NVIDIA, 2023; accessed 2026-08-14]. “GPU utilization” alone therefore tells only part of the story.

Text version of the map

  1. Storage holds the model file. It feeds RAM when the model loads.
  2. RAM holds CPU weights, CPU-side KV cache, working data, and staged data for a discrete GPU.
  3. The CPU runs CPU layers. It also handles setup, tokenization, sampling, and orchestration around GPU work.
  4. PCIe and motherboard topology connect system memory to discrete GPUs. Hybrid and multi-GPU modes depend on this transfer path.
  5. VRAM holds GPU-resident weights, KV cache, and compute buffers. GPU cores operate on that data.
  6. The software backend supplies the kernels and device support. Weak support can waste strong hardware or block it outright.
  7. Power and cooling let processors sustain clocks. Heat or power limits can reduce speed during long runs.

Size the workload before buying hardware

Three estimates catch most capacity problems. They are planning tools, not promises. Model formats add metadata. Some tensors stay at higher precision. Runtimes also reserve temporary buffers.

Weight memory

parameters × bits per weight ÷ 8

An 8-billion-parameter model at a perfect 4 bits per weight would need 4 GB, or about 3.73 GiB, for raw weights. A real Q4 file is larger because “Q4” is not a perfect four-bit package. For example, llama.cpp lists a 4.9 GB Q4_K_M file for one Llama 3.1 8B example [llama.cpp quantization guide, accessed 2026-08-14].

KV-cache memory

tokens × layers × 2 × KV heads × head size × bytes per element × concurrent sequences

The factor of two covers keys and values. A hypothetical 32-layer model with 8 KV heads, a head size of 128, FP16 cache values, 4,096 tokens, and one sequence needs 536,870,912 bytes: 512 MiB. Four concurrent sequences need about 2 GiB. Models with full multi-head attention can need much more. Grouped-query and multi-query attention reduce the number of KV heads [NVIDIA, 2023; accessed 2026-08-14].

Total working memory

weights + KV cache + compute buffers + runtime headroom

Leave room for the operating system, display use, the backend, and temporary allocations. A model file that is smaller than VRAM can still fail to load.

GB is not GiB. One decimal gigabyte is 1,000,000,000 bytes. One binary gibibyte is 1,073,741,824 bytes [NIST binary-prefix reference, accessed 2026-08-14]. Also separate a vendor’s theoretical bandwidth from achieved bandwidth. Real kernels lose time to access patterns, overhead, synchronization, and unsupported operations.

CPU only

CPU inference is the simple baseline. The model sits in system RAM. The CPU reads each layer’s weights and performs the math. Quantized GGUF models make this practical on ordinary machines because they cut both capacity needs and memory traffic. Quantization can also reduce quality, so smaller is not automatically better [llama.cpp quantization guide, accessed 2026-08-14].

Generation often streams much of the model for each token. That makes RAM bandwidth a hard ceiling. More CPU cores help only until they compete for the same memory channels. Prompt processing can still benefit from compute and vector instructions.

One GPU, with or without help from the CPU

Full offload keeps the active model in VRAM and avoids repeated PCIe crossings. This is usually the cleanest path for one interactive user. If the model does not fit, a runtime such as llama.cpp can place only some layers on the GPU. That can beat CPU-only inference, but every token must still traverse the CPU layers. The slow section controls the lap time.

KV-cache offload solves a different capacity problem. Hugging Face can keep the current layer’s cache on the GPU while it moves other layer caches to the CPU. This saves VRAM but adds transfer work and can reduce generation throughput [Hugging Face KV-cache guide, accessed 2026-08-14].

Several GPUs: three different jobs

“Multi-GPU” does not describe one design. A layer split places contiguous layers on different GPUs. It mainly joins their capacity. Tensor parallelism splits work inside each layer, so GPUs must exchange partial results often. Data parallelism copies the full model to each GPU and sends each copy independent requests.

Current llama.cpp documentation calls its layer split the default and most compatible choice. It calls tensor splitting experimental and warns that interconnect speed matters much more. It also notes that multi-GPU can run slower than one GPU when communication becomes the bottleneck [llama.cpp multi-GPU guide, accessed 2026-08-14]. vLLM defines data-parallel deployment as replicated model instances that process independent request batches [vLLM data-parallel guide, accessed 2026-08-14].

Unified memory, disk, and another machine

A unified-memory system removes the separate RAM and VRAM pools. Apple’s MLX documentation states that the CPU and GPU have direct access to the same memory pool, so an array does not need a device-to-device copy before either processor uses it [MLX unified-memory guide, accessed 2026-08-14]. That simplifies placement. It does not create infinite capacity or bandwidth.

Disk offload extends capacity again, but each needed layer must travel from disk to RAM and then to the accelerator. Hugging Face calls hard-drive placement the slowest automatic option and notes the transfer overhead [Hugging Face Accelerate guide, accessed 2026-08-14]. A second machine replaces disk latency with network latency and distributed coordination. Both are capacity tools before they are speed tools.

What moves the bottleneck?

Quantization
Smaller weights use less memory and require less bandwidth. Very small formats can trade away model quality or use kernels that are less efficient on a given backend.
Context length
More tokens grow the KV cache and increase attention work. The exact rate depends on the model architecture and cache type.
Batch size and concurrency
More work in parallel can use GPU compute better, but each active sequence needs cache space. Throughput can rise while latency and memory use also rise.
Dense versus MoE
A dense model uses all of its layers for each token. A mixture-of-experts model routes each token through a subset of experts, but the system may still need to store a much larger set of weights. Capacity and expert-routing communication can dominate even when active compute is lower.
Multimodal inputs
Vision or audio projectors add weights, buffers, and prompt-processing work. Image resolution and input count can add many effective tokens.
Backend and kernels
The driver and runtime must support the device, model operations, data types, and quantization format. Peak hardware figures mean little when the backend falls back or uses weak kernels.

Case study: the Green Room

The Green Room has an Intel i5-6500, 16 GB of DDR4-2133, a Radeon R9 390 with 8 GB of GDDR5, an ASRock Fatal1ty Z270 Gaming K4, a 750 W PSU, and a 230 GB hard drive from 2014 [Green Room initial setup]. It is a fine machine for learning where the edges are. It has quite a few edges.

Capacity: small quantized models are the sensible target

The 8 GB R9 390 can hold some 7–8B-class Q4 model files with limited context, but that is not a guarantee [llama.cpp model-size example, accessed 2026-08-14] [AMD specifications, accessed 2026-08-14]. The GGUF file size, KV cache, compute buffers, display use, and backend allocations all count. The 16 GB of system RAM gives CPU inference more room, yet Windows and the runtime need their share. Paging a model to the old hard drive would turn a capacity problem into a storage problem.

Bandwidth: a large theoretical gap

Intel specifies a maximum memory bandwidth of 34.1 GB/s for the i5-6500’s dual-channel controller [Intel specifications, accessed 2026-08-14]. AMD specifies up to 384 GB/s for the R9 390’s VRAM [AMD specifications, accessed 2026-08-14]. Dividing those figures gives a theoretical ratio of about 11.3 to 1.

That ratio is not a benchmark. Different kernels, quantization formats, memory-access patterns, and driver paths change achieved speed. The GPU wins only if the backend can use it well and the working set stays in VRAM.

Software: the biggest question mark

AMD lists the R9 390 under Windows legacy drivers and states that it plans no additional driver releases [AMD driver page, accessed 2026-08-14]. AMD’s current Radeon ROCm support tables list modern Radeon 9000 and selected 7000-series devices, not the R9 390 [AMD ROCm compatibility tables, accessed 2026-08-14].

That makes ROCm a poor assumption for this box. llama.cpp documents a Vulkan backend and Windows build path [llama.cpp build guide, accessed 2026-08-14]. Vulkan is therefore the practical GPU path to test first. It is not a promise of full offload, stable kernels, or good speed on this legacy card. CPU-only llama.cpp remains the control test.

A second GPU is a bad first upgrade

The board’s first long slot runs at PCIe 3.0 ×16. ASRock specifies the second long slot at ×4, and it can drop to ×2 when either of two nearby slots is occupied [ASRock specifications, accessed 2026-08-14]. A second GPU would also add driver, cooling, power, and model-splitting problems. A 750 W label alone does not prove that the unit, cables, rails, and thermals can support any chosen pair.

Layer splitting might add capacity, but the weaker slot and old platform would constrain transfers. Tensor parallelism would ask even more from that connection. On this board, two GPUs could produce twice the heat and one very educational bottleneck.

Upgrade in the order the measurements point

  1. Loading is slow or the system pages: replace the HDD with an SSD.
  2. The model does not fit: add the type of memory used by the chosen mode. That means RAM for CPU work or VRAM for full GPU offload.
  3. Generation is slow after the model fits: favor supported hardware with high memory bandwidth and an efficient backend.
  4. Prompt processing is slow: favor stronger accelerator compute and kernels.
  5. CPU and hybrid modes stay slow: replace the CPU, memory, and motherboard as one platform. Upgrading one old link leaves the other old links in place.

Benchmark the path, not the marketing number

Use one model file, prompt, context size, output length, and software build. Warm up the model. Then change one variable at a time: CPU threads, GPU-offloaded layers, cache type, context length, or parallel sequences.

llama-bench separates prompt-processing tests from text-generation tests, repeats runs, and reports average tokens per second. Its measurements exclude tokenization and sampling, so a full application can feel slower [llama.cpp benchmark guide, accessed 2026-08-14].

For the Green Room, I would compare CPU only, a small partial Vulkan offload, and the largest stable offload that fits. I would record failures too. An out-of-memory error, a driver crash, or a slower hybrid result identifies a limit as clearly as a tokens-per-second number.

Inference is the easy memory case

Inference mainly needs weights, KV cache, activations for the current work, and runtime buffers. Fine-tuning must also retain more activations and gradients. Full training adds optimizer state and often higher-precision master weights. Batch size then has a much larger effect on memory.

Techniques such as parameter-efficient fine-tuning, activation checkpointing, gradient accumulation, and optimizer-state sharding change that equation. They deserve their own map. The practical lesson here is simple: hardware that fits a model for inference may still be far too small to train it.

Find your bottleneck

  • Capacity: Do weights, KV cache, buffers, and headroom fit without paging or out-of-memory errors?
  • Bandwidth: Does generation stay slow while compute units wait for memory?
  • Compute: Is prompt processing slow even when the model and data remain on the accelerator?
  • Transfer: Does partial offload or a second GPU add little speed or make latency worse?
  • Software: Does the backend support the device, data type, model operations, and quantization format?
  • Power and cooling: Do clocks fall, temperatures climb, or errors appear during a sustained run?

Measure the phase that feels slow. Fix that limit. Then measure again, because the reward for removing one bottleneck is meeting the next one.
